## 1. Goal and pass criteria

From `roadmap.md` P0-S10 and `context_pack.md` §4: resolve **U13** — can the service downscale frames
to 320×240 RGB in RAM and stream them over `\\.\pipe\kenali.preview` at **≥ 15 fps** within the
NFR-02 CPU budget (≤ 5 % of one core), RAM-only, zeroized, no codec, no disk?

Pass conditions (all OWNER-run in the VM):
1. `\\.\pipe\kenali.preview` exists with SDDL `D:P(A;;GA;;;SY)(A;;GA;;;BA)` and the same create
   flags as admin: `FILE_FLAG_FIRST_PIPE_INSTANCE`, `PIPE_REJECT_REMOTE_CLIENTS`, message mode.
2. It exists **only** while an enrolment/calibration window is open; `EndPreview` / wizard end / app
   exit closes it. It is absent at ordinary logon.
3. The service downscales in RAM with `fast_image_resize` to **320×240 RGB** (230,400 B) and sends
   raw RGB over the wire — no JPEG/PNG, no codec dependency, no disk writes.
4. Each preview message is **≤ 512 KB**; the decoder rejects oversized messages.
5. Sustained throughput is **≥ 15 fps** measured in the VM, with CPU cost within NFR-02 (≤ 5 % of
   one core) for downscale + send.
6. The UI renders straight from RAM and zeroizes its buffers on window close / app exit; service
   preview buffers are zeroized on every path.
7. Server-PID anti-squatting applies (client verifies server PID against SCM PID for `KenaliSvc`).

## 3. Offline-verified facts (from `context_pack.md` §3.8/§8/§9 and the Wave-3 plan)

These are **(a) OFFLINE FACTS** — not runtime observations.

- **Preview channel (`context_pack.md` §3.8):** the service downscales in RAM with `fast_image_resize`
  (already pinned) to **320×240 RGB** and streams on `\\.\pipe\kenali.preview`, message-mode,
  cap **≤ 512 KB/message** (320×240×3 = 230,400 B fits), ≈ **15 fps** target, only while an
  enrolment/calibration window is open. The UI renders straight from RAM and zeroizes buffers when
  the window closes or the app exits. **No encoder/codec**: raw RGB, never JPEG/PNG on the wire,
  never on disk.
- **Pipe rules (`context_pack.md` §9):** preview DACL = same as admin
  `D:P(A;;GA;;;SY)(A;;GA;;;BA)`; create flags = `FILE_FLAG_FIRST_PIPE_INSTANCE`, overlapped,
  message mode, `PIPE_REJECT_REMOTE_CLIENTS`, small max instances; instance exists **only during
  enrolment/calibration windows**. Server verifies client (elevated Administrator, signed Kenali
  binary in `C:\Program Files\Kenali\<version>\`); client verifies server PID against SCM PID for
  `KenaliSvc`. Message cap ≤ 512 KB. Lifecycle: opened by `BeginPreview`, closed by `EndPreview` /
  wizard end / app exit.
- **Wire type (`context_pack.md` §8):** `PreviewFrame { w: u16, h: u16, rgb: Bytes }` on the preview
  pipe only. IPC caps: preview frames ≤ 512 KB.
- **Ownership (`context_pack.md` §3.3, §12, §2.17):** the UI never opens the camera; the service owns
  it exclusively and streams downscaled preview during enrolment/calibration; the wizard warns the
  user to close other camera apps to avoid contention.
- **Planned seam (Wave-3 plan):** preview pipe path = `kenali_winapi::pipe_server::PREVIEW_PIPE_PATH`;
  SDDL = `PREVIEW_PIPE_SDDL`; service `kenali_service::pipe_loop::serve_preview_pipe` +
  `preview.rs` manage lifecycle with RAM-only/zeroized frames (`zeroize.workspace = true` on
  `kenali-service`). These are plans; runtime behavior is **VERIFY**.

## 4. Procedure — exact manual VM steps (OWNER only)

These are **(b) OWNER MANUAL STEPS**, run by hand in the VM after the checkpoint. The agent runs none.

1. **Prepare the VM.** Checkpoint; record §2 rows; keep the reference camera free (close other camera
   apps). Confirm the NFR-02 budget from `docs/prd.md`.
2. **Build + install.** Build `kenali-svc` / `kenali-winapi` (W3-05/W3-08) and the Wave-4 UI preview
   worker for MSVC; install in the VM via the gated `xtask install --vm`. The host type-checks only.
3. **Confirm the pipe is absent at logon.** Before any enrolment/preview, confirm
   `\\.\pipe\kenali.preview` does not exist (e.g. `pipelist` / a handle viewer). This proves the
   lifecycle gate.
4. **Open a preview window.** In the UI, begin enrolment/calibration (`BeginPreview`). Confirm the
   pipe appears with SDDL `D:P(A;;GA;;;SY)(A;;GA;;;BA)`, message mode and remote clients rejected;
   confirm `FIRST_PIPE_INSTANCE` (a second create fails) and server-PID anti-squatting.
5. **Confirm frame format + cap.** Inspect received messages: each is `PreviewFrame { w: 320, h: 240,
   rgb }` with exactly 230,400 B payload, raw RGB downscaled via `fast_image_resize`. Confirm no
   JPEG/PNG magic bytes, no codec DLL loaded and no frame file written to disk (monitor with a file
   handle viewer / ProcMon). Confirm the decoder rejects a message > 512 KB.
6. **Measure throughput.** At a steady camera feed, count received frames over ≥ 10 s and compute
   fps; confirm **≥ 15 fps** sustained. Record p50/p95 inter-frame interval.
7. **Measure CPU cost.** While streaming, measure service CPU for the downscale + send path with
   `typeperf` / ETW / Task Manager; confirm ≤ 5 % of one core (NFR-02). Record the number of cores
   and the per-core percentage.
8. **Confirm zeroization + lifecycle close.** End preview (`EndPreview` / close wizard / exit UI);
   confirm the pipe is removed and that service and UI preview buffers are zeroized (debug-build
   inspection or a test hook). Confirm no frame bytes remain on disk or in logs.
9. **Contention note.** With another camera app open, confirm the wizard's warning behavior and that
   preview degrades gracefully rather than crashing.
10. **Reset.** Leave the VM with no preview window open and the service in a known-good state.
