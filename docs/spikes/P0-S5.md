**Safety warning (non-negotiable):**
- Never load `onnxruntime.dll` by relative path or from `System32`. Windows ships its own, older ORT;
  the wrong DLL produces `0xc000007b` and is a DLL-hijack risk (`context_pack.md` §3.4 [R36]).
- **Do not use DirectML** — Microsoft lists it as "sustained engineering" [R20][R21]. CPU first.
- Never commit model weights / ONNX files (`context_pack.md` §2.15). Models are hash-verified against
  the committed `models/models.lock` before session creation.

Terminology: "VM|virtual machine" means the disposable Windows 11 x64 VM — never this WSL2 host.

3. No DirectML execution provider is used; CPU is the execution provider.
4. Session settings are applied explicitly: intra-op threads = `min(4, physical cores)`, inter-op = 1,

   service start.
5. Each model loads only after its SHA-256 matches `models/models.lock`.
6. INT8 vs FP32 accuracy and latency on YuNet (detect) and SFace (embed) are measured and recorded;
   channel order / scaling cross-checked against OpenCV `FaceRecognizerSF` on a few images.
7. `tract` (pure Rust) is shown to be a viable benchmark fallback if ORT proves problematic.

## 3. Offline-verified facts (from `context_pack.md` §3.4/§3.5 and the Wave-3 plan)

These are **(a) OFFLINE FACTS** — not runtime observations.

- **`ort` pin [R18]:** newest confirmed **`2.0.0-rc.13`** (wraps ONNX Runtime 1.28). Pin with
  `=2.0.0-rc.13`. Re-check crates.io at bootstrap for a stable `2.0.0` — **VERIFY**. Since rc.11 the
  bundled ORT build favours low-resource edge inference over throughput [R19] — a good default.
- **`load-dynamic` + absolute path [R36]:** use the `load-dynamic` feature and load Kenali's own
  `onnxruntime.dll` by absolute path (`ort::init_from(path)`). Windows ships its own older ORT;
  picking the wrong one produces **`0xc000007b`** and is a DLL-hijack risk.
- **No DirectML [R20][R21]:** Microsoft lists DirectML as "sustained engineering", Windows ML is the
  forward path. CPU first; hardware EPs are a later optional upgrade.
- **Session settings (names VERIFY on docs.rs):** intra-op threads = `min(4, physical cores)`,
  inter-op = 1, graph optimisation = all, reuse sessions, pre-allocated input tensors, one dummy
  inference at service start.
- **`tract` fallback:** pure Rust, the benchmark fallback if ORT proves problematic.
- **Models [R22]–[R27]:** YuNet (detect, BGR raw 0–255 NCHW, H/W padded to multiples of 32),
  SFace (embed, 112×112 RGB raw 0–255 NCHW → 128-d, L2-normalise; FP32 ≈ 36.9 MB, an INT8 variant
  exists), MiniFASNet V2 + V1SE (PAD). OpenCV reference SFace threshold cosine 0.363 is **not**
  security-calibrated — calibrate our own (`context_pack.md` §3.5).
- **Indicative CPU timings [R24]:** OpenCV DNN on i7-12700K-class — YuNet @160×120 ≈ 1.45 ms,
  SFace @112×112 ≈ 8.65 ms. Order-of-magnitude only; **VERIFY** on our ORT/CPU.
- **Planned types (Wave-3 plan):** `kenali_vision::onnx::{OrtDetector, OrtAligner, OrtEmbedder,
  OrtPadClassifier}` implement the four merged traits; `verify_model_hash` checks SHA-256 against
  `models.lock`; pinned filenames `yunet.onnx`, `sface.onnx`, `minifasnet_v2.onnx`,
  `minifasnet_v1se.onnx` with `onnxruntime.dll` recorded against the `ort =2.0.0-rc.13` pin.

## 4. Procedure — exact manual VM steps (OWNER only)

These are **(b) OWNER MANUAL STEPS**, run by hand in the VM after the checkpoint. The agent runs none.

1. **Prepare the VM.** Checkpoint; record §2 rows; confirm CPU core count (for intra-op setting) and
   the reference camera for sample frames.
2. **Pin check.** Re-check crates.io for `ort` stable `2.0.0`; record whether `=2.0.0-rc.13` stays.
   Confirm `Cargo.lock` resolves the pinned version and the `load-dynamic` feature is enabled.
3. **Place the DLL + models by absolute path.** Put Kenali's `onnxruntime.dll` and the pinned models
   in `C:\Program Files\Kenali\<version>\` (or `KENALI_MODEL_DIR`). Record the absolute path and SHA-256
   of the DLL and each `.onnx`. Confirm no `.onnx` is committed to the repo.
4. **Load the correct DLL.** Call `ort::init_from(absolute_path)` and confirm the loaded ORT version
   matches Kenali's bundled DLL (not the Windows/System32 copy). Deliberately attempt a relative /
   wrong path in a throwaway test and confirm the `0xc000007b` failure mode is understood; never use
   that path in the product.
5. **Confirm no DirectML.** Inspect session creation: CPU execution provider only; no DirectML EP.
6. **Confirm session settings.** Verify intra-op = `min(4, physical cores)`, inter-op = 1, graph opt =
   all, session reuse, preallocated input tensors, and the one dummy inference at start. Record any
   setting that differs and why.
7. **Hash verification.** With a model whose SHA-256 does not match `models.lock`, confirm
   `verify_model_hash` refuses to create a session; with the correct model, confirm it loads.
8. **INT8 vs FP32 — accuracy.** On a small representative image set (OWNER-provided, not committed),
   run YuNet detect and SFace embed in both INT8 and FP32. Compare detections/embeddings and cosine
   scores; cross-check SFace channel order and scaling against OpenCV `FaceRecognizerSF` on a few
   images. Record any accuracy delta.
9. **INT8 vs FP32 — latency.** Warm up, then measure per-stage latency (YuNet @160×120, SFace
   @112×112, PAD) for both variants; record p50/p95 and compare with the indicative [R24] numbers
   and the NFR budgets (`docs/prd.md`). Note which variant is the better default for our CPU.
10. **`tract` fallback.** Run the benchmark fallback on the same images; confirm it produces
    comparable outputs and record its latency (slower is acceptable — it is a fallback).
11. **Reset.** Leave the VM with the chosen ORT pin, DLL and model variants in place; no real face
    data retained.

`load-dynamic`, absolute-path DLL, CPU-only) is consistent with the security goals; nothing here
establishes that inference is unsafe to attempt in a checkpointed VM.

This decision is **provisional** — no Windows runtime, accuracy or latency evidence exists on this
host. It becomes:
- **GO** if the correct DLL loads by absolute path, no DirectML is used, session settings apply,
  hash verification works and a default INT8/FP32 variant is chosen with acceptable accuracy/latency;
- **PIVOT** if ORT proves problematic (load failures, wrong-DLL issues, unacceptable latency) —
  evaluate the `tract` fallback and revisit the pin/variant;
- **STOP** if the correct DLL cannot be loaded safely by absolute path or no variant meets the
  accuracy/latency bar — do not proceed to calibration.
