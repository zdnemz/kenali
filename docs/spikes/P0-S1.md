## 3. Offline-verified CP facts (from `context_pack.md` §3.1)

These are **(a) OFFLINE FACTS**, transcribed from the docs, not observations on this host.

- **In-process COM server:** a CP is loaded by `LogonUI.exe` (and may be loaded by Explorer for
  some UAC/CredUI prompts). Decline scenarios you do not support.
- **DLL exports:** `DllGetClassObject` and `DllCanUnloadNow` (module-wide ref-count; `S_OK` only
  at zero). Registration is done by `xtask`, **not** by `DllRegisterServer`.
- **Call order (no filter):**
  `DllGetClassObject` → `IClassFactory::CreateInstance(ICredentialProvider)` →
  `SetUsageScenario(cpus, flags)` → *( `SetSerialization` for RDP/CredUI — we decline )* →
  *( `SetUserArray` if `ICredentialProviderSetUserArray` is implemented )* →
  `Advise(events, ctx)` → `GetCredentialCount(count, default, autologon)` →
  `GetCredentialAt(i)` → `GetFieldDescriptorCount/At` → per-credential field callbacks →
  `Credential::Advise` → `SetSelected` → … → on submit `GetSerialization` → `ReportResult` →
  `UnAdvise`.
- **Declining a scenario:** return `E_NOTIMPL` from `SetUsageScenario`; the provider is then
  unloaded. The spike declines everything except `CPUS_UNLOCK_WORKSTATION`.
- **Autologon is not guaranteed:** `GetCredentialCount` sets `*pdwDefault` (tile index) and
  `*pbAutoLogonWithDefault = TRUE`, and `SetSelected` returns TRUE. On Windows 10+, Windows shows a
  sign-in button as a **speed bump** when autologon is considered inappropriate. The spike never
  submits, so autologon is out of scope here.
- **Asynchronous results:** to act on a later match, call
  `ICredentialProviderEvents::CredentialsChanged(advise_context)` so LogonUI re-queries
  `GetCredentialCount`.
- **Secret hygiene:** `SetDeselected` must scrub every secret held by the credential object.
- **Visibility:** the allowed-SID guard shows the tile only for the enrolled user's SID.
- **Registration keys (native x64 view):** the CLSID is `KENALI_CP_CLSID` (committed constant,
  value `192a78ba-404d-4f82-8625-4b0c11d05f21`, `crates/kenali-winapi/src/com.rs` — **never** reuse
  a GUID from a blog). `HKLM\SOFTWARE\Microsoft\Windows\CurrentVersion\Authentication\Credential
  Providers\{CLSID}` (default = display name); `HKCR\CLSID\{CLSID}` (default = name);
  `HKCR\CLSID\{CLSID}\InprocServer32` (default = **absolute** DLL path, `ThreadingModel` =
  `Apartment`). No reboot needed — lock or sign out to test. DLL lives in an admin-write-only,
  versioned folder.
- **Pipe:** `\\.\pipe\kenali.auth`, SDDL `D:P(A;;GA;;;SY)` (SYSTEM-only). Not exercised by this
  spike (the tile never submits).
- **Kill switch:** a `REG_DWORD` `Disabled=1` under the provider's CLSID key in
  `…\Authentication\Credential Providers\` takes effect at the next session creation
  (`context_pack.md` §3.7). Kenali's own `HKLM\SOFTWARE\Kenali\Disabled=1` makes the CP return
  `E_NOTIMPL` (`dev_safety_runbook.md` §3).
- **NOT in scope / do-not-do:** no CP filter, no ML/network/async runtime inside the CP, no
  similarity scores, never filter or delay the password/PIN providers (`context_pack.md` §12).

## 4. Procedure — exact manual VM steps (OWNER only)

These are **(b) OWNER MANUAL STEPS**. The OWNER runs them by hand inside the Windows VM, after the
checkpoint from `dev_safety_runbook.md` §1/§2 is in place. The agent does not run any of them.

1. **Prepare the VM.** Take a checkpoint / restore point before any install. Confirm the §2
   pre-flight rows are recorded and satisfy `dev_safety_runbook.md` §2. Keep a second local admin
   account with a working password available (assumption A8). Do all of this in the **VM**, not on
   the physical host's main account.
2. **Build the DLL.** From the versioned checkout, build the CP for `x86_64-pc-windows-msvc`
   (`cargo xtask build [--release]`, `context_pack.md` §10). Confirm the artifact lands in the
   versioned install layout `C:\Program Files\Kenali\<version>\kenali-cp.dll` (the code from W2-03
   in `crates/kenali-cp/src/`), with the static CRT and CP baseline CPU flags from
   `context_pack.md` §10. Do **not** edit a registered DLL in place.
3. **Install via the gated xtask.** In an elevated PowerShell in the VM, set the gate yourself and
   run the installer:
   ```powershell
   $env:KENALI_ALLOW_INSTALL = '1'
   cargo xtask install --vm
   ```
   (`xtask/src/install.rs` from W2-04; `context_pack.md` §10, `dev_safety_runbook.md` §1). The
   command refuses to run unless `KENALI_ALLOW_INSTALL=1` and prints the safety pre-flight. Read and
   satisfy that checklist before proceeding.
4. **Register the CLSID.** Confirm registration uses the committed constant `KENALI_CP_CLSID` =
   `192a78ba-404d-4f82-8625-4b0c11d05f21` (`crates/kenali-winapi/src/com.rs`) under the three keys
   in §3, with `ThreadingModel=Apartment` and the **absolute** versioned DLL path in
   `InprocServer32`. Registration is by `xtask`, **not** `DllRegisterServer`/`regsvr32` by hand.
5. **Lock or sign out** (no OS reboot needed) and observe the sign-in screen.
6. **Confirm the `"spike"` tile appears only for the allowed SID.** Sign in as the enrolled test
   SID and note the tile labelled **"spike"**. Sign in as a different SID and confirm the tile is
   absent. This exercises the allowed-SID guard (`crates/kenali-cp/src/allowed_sid.rs`).
7. **Confirm it never submits.** Select the `"spike"` tile and interact with it. No serialization
   is sent, no auth pipe message is produced, no `KERB_INTERACTIVE_UNLOCK_LOGON` is packed, and no
   `ReportResult` success path runs. The tile must only display; `GetSerialization` never yields a
   submission for this spike.
8. **Verify the password tile still works.** At the same screen, use the normal password tile to
   sign in. It must work with no delay and must not be hidden, filtered or replaced
   (`dev_safety_runbook.md` §1).
9. **Verify the kill switch.** Set `Disabled=1` under the provider CLSID key **and**
   `HKLM\SOFTWARE\Kenali\Disabled=1` per `dev_safety_runbook.md` §3, then lock / sign out and back
   in. Confirm the `"spike"` tile is gone at the next session creation and the password tile still
   works. Re-enable (delete or zero both values) and confirm the tile returns.
10. **Verify recovery drills in the VM** per `dev_safety_runbook.md` §4: kill the service / service
    down (R-A), kill switch (R-B, overlap with step 9), **Safe Mode** (R-C — only the built-in
    password provider loads), and **WinRE** (R-D — offline-disable the CP or rename the DLL if Safe
    Mode is unreachable). Record date, machine and result in §7.
11. **Roll back** (R-E, `dev_safety_runbook.md` §4): if this build is bad, run
    `cargo xtask rollback` (OWNER, in the VM) to repoint `InprocServer32` at the previous versioned
    DLL and restore prior registration; lock / sign out and confirm the prior version loads. If
    rollback fails, fall back to R-D (rename DLL / offline disable). Never edit a registered DLL in
    place.

  `RevokeInterfaceFromGlobal`, with the advised context carried through. Record the exact COM
  apartment (`ThreadingModel=Apartment`) behaviour observed and what happens if `CredentialsChanged`
  is called from the wrong thread.
