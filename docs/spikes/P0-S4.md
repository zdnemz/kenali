CNG `MS_PLATFORM_CRYPTO_PROVIDER`, a non-exportable persisted RSA-2048 key finalized with

Pass conditions (all OWNER-run in the VM):
1. `MS_PLATFORM_CRYPTO_PROVIDER` opens and a persisted, **non-exportable RSA-2048** key is created
   with `NCRYPT_MACHINE_KEY_FLAG`, finalized with `NCryptFinalizeKey`, and opened again consistently.
2. A 32-byte DEK is wrapped (RSA-2048-OAEP-SHA256) and then unwrapped correctly (round-trip).
3. Password/template payloads are encrypted with **XChaCha20-Poly1305** using the DEK; the DEK itself
   is the only thing wrapped by the TPM RSA key (hybrid scheme).
4. Unwrap latency p50/p95 is measured over enough iterations and compared with the NFR-01 budget.
5. `MS_KEY_STORAGE_PROVIDER` software fallback works **only** behind `--allow-weak-keystore` with a
   loud warning; absent the flag, the software path is refused.
6. AAD = magic ‖ version ‖ file type ‖ user SID is bound and verified; template AEAD round-trips.
7. No key material, DEK, password or template is ever exported, logged or written to disk raw.

## 3. Offline-verified facts (from `context_pack.md` §3.6 and the Wave-3 plan)

These are **(a) OFFLINE FACTS** — not runtime observations.

- **CNG flow [R29]:** `NCryptOpenStorageProvider(MS_PLATFORM_CRYPTO_PROVIDER)` →
  `NCryptCreatePersistedKey` → **`NCryptFinalizeKey`** (the key is not stored or usable before
  finalize). Use `NCRYPT_MACHINE_KEY_FLAG` consistently on create **and** open, otherwise the key is
  user-scoped. Creating the key needs elevation. Mark it non-exportable.
- **Hybrid encryption [R29]:** TPMs reliably support RSA. RSA-2048-OAEP-SHA256 encrypts at most
  **190 bytes**, so use a hybrid scheme: a random **32-byte DEK**; password and templates encrypted
  with **XChaCha20-Poly1305**; the DEK wrapped by the TPM RSA key.
- **Provider fallback [R30]:** `MS_KEY_STORAGE_PROVIDER` (software) only behind an explicit
  `--allow-weak-keystore` flag and a loud warning (Chromium selects TPM vs software the same way).
  Windows **VBS key protection** is a possible middle tier — **VERIFY** flags [R31].
- **AEAD:** `chacha20poly1305` (XChaCha20-Poly1305), random 24-byte nonce, AAD = magic ‖ version ‖
  file type ‖ user SID.
- **Latency unknown:** TPM unwrap latency is explicitly unknown and must be measured here (**U6**).
  Assume BitLocker is on; TPM wrapping is defence in depth, not a substitute.
- **Planned type (Wave-3 plan):** `kenali_winapi::tpm::TpmKeyHierarchy` implements
  `kenali_store::keys::KeyHierarchy`; `open(allow_weak_keystore: bool) -> Result<Self, KeyError>`;
  uses `MS_PLATFORM_CRYPTO_PROVIDER`, with `MS_KEY_STORAGE_PROVIDER` only behind the weak flag;
  `NCryptFinalizeKey` before use; `NCRYPT_MACHINE_KEY_FLAG` on create/open; non-exportable RSA-2048 +
  OAEP-SHA256 wraps the 32-byte DEK. This is a plan; runtime behavior is **VERIFY**.

## 4. Procedure — exact manual VM steps (OWNER only)

These are **(b) OWNER MANUAL STEPS**, run by hand in the VM after the checkpoint. The agent runs none.

1. **Prepare the VM.** Checkpoint; record §2 rows (TPM present, BitLocker assumed on, elevation).
2. **Build.** Build `kenali-svc` / `kenali-winapi` `tpm.rs` (`TpmKeyHierarchy`, W3-05) for MSVC. The
   host only type-checks it; no key operation runs here.
3. **Create the TPM key.** In an elevated VM context, open `MS_PLATFORM_CRYPTO_PROVIDER`, create a
   persisted **non-exportable RSA-2048** key with `NCRYPT_MACHINE_KEY_FLAG`, call
   `NCryptFinalizeKey`, and reopen it with the same flag. Confirm creation is refused without
   elevation. Record any error codes.
4. **Confirm non-exportability.** Attempt to export the private key; confirm it is refused. Confirm
   no key material appears in logs or on disk.
5. **Wrap/unwrap round-trip.** Generate a random 32-byte DEK, wrap it with RSA-2048-OAEP-SHA256,
   unwrap it, and confirm byte-for-byte equality. Confirm a tampered ciphertext is rejected.
6. **AEAD round-trip.** Encrypt a dummy password/template payload with XChaCha20-Poly1305 using the
   DEK, random 24-byte nonce and AAD = magic ‖ version ‖ file type ‖ user SID; decrypt and confirm
   equality. Confirm AAD tampering is rejected. Use only dummy data — no real face data or password.
7. **Measure unwrap latency (the U6 deliverable).** Repeat the DEK unwrap (and, separately, the
   XChaCha20-Poly1305 decrypt) enough times to be stable — e.g. ≥ 100 iterations after a warm-up of
   ≥ 10. Record **cold** (first after provider open) and **warm** p50/p95/min/max, and compare against
   the NFR-01 budget in `docs/prd.md`. Note whether the operation blocks and for how long at the
   lock screen.
8. **Software fallback.** Repeat steps 3–6 with `MS_KEY_STORAGE_PROVIDER`: confirm it is **refused**
   without `--allow-weak-keystore`, and that with the flag it works and emits a **loud warning**.
   Record the exact warning text/Event Log entry.
9. **VSA check (U10 link).** If P0-S2 chose a virtual service account, confirm the TPM key open/wrap
   works under that account with `NCRYPT_MACHINE_KEY_FLAG`. Record the result.
10. **Reset.** Delete the spike key from the VM's TPM/CNG store if practical (or note that it remains
    in the disposable VM); leave no key material in docs/logs.
